# 分布式通信框架

## 第一步：确定基础设施层

### 1. 网络IO抽象层

**目标**：封装底层的socket操作，提供统一的非阻塞IO接口

**需要做的事情**：

- **Socket封装**：
  - 创建非阻塞socket
  - 设置socket选项（TCP_NODELAY、SO_REUSEADDR等）
  - 绑定、监听、连接、接受连接
  - 读写操作（非阻塞）
  - 关闭连接
- **地址抽象**：
  - 统一IPv4/IPv6的地址表示
  - 支持域名解析（可能需要异步DNS）
  - 地址的序列化和反序列化
- **缓冲区管理**：
  - 接收缓冲区（处理粘包、半包）
  - 发送缓冲区（处理发送不完的情况）
  - 缓冲区的扩容和收缩策略
  - 是否需要环形缓冲区？

**关键决策**：

- 缓冲区初始大小？（如4KB、8KB）
- 最大大小限制？（防止内存耗尽）
- 是否使用对象池？

------

### 2. 事件循环（Reactor）

**目标**：监听IO事件，分发到对应的处理函数

**需要做的事情**：

- **事件类型定义**：
  - 可读事件
  - 可写事件
  - 错误事件
  - 关闭事件
- **事件注册机制**：
  - 注册某个fd的某个事件
  - 注销事件
  - 修改事件（如从只读改为读写）
- **事件循环**：
  - 主循环逻辑（epoll_wait/kqueue）
  - 超时处理（epoll_wait的timeout参数）
  - 信号处理（如何优雅退出）
  - 唤醒机制（如何从其他线程唤醒事件循环）
- **线程模型**：
  - 单线程Reactor？
  - 多线程Reactor？（主Reactor + 多个子Reactor）
  - 如何分配连接到不同的Reactor？

**关键决策**：

- 边缘触发（ET）还是水平触发（LT）？
  - ET性能更好，但编程更复杂
  - LT更安全，不容易丢事件
- 每个Reactor管理多少连接？
  - 太少：线程切换开销大
  - 太多：单线程处理不过来
- 如何唤醒Reactor？
  - eventfd（Linux）
  - pipe
  - socketpair

------

### 3. 定时器管理

**目标**：高效管理大量定时器（用于超时、心跳等）

**需要做的事情**：

- **定时器抽象**：
  - 定时器ID（用于取消）
  - 超时时间（绝对时间还是相对时间？）
  - 回调函数
  - 是否重复触发？
- **定时器容器**：
  - 选择数据结构（最小堆、时间轮、红黑树）
  - 插入定时器
  - 删除定时器
  - 查找最近的超时时间
- **与事件循环集成**：
  - 如何确定epoll_wait的timeout？
  - 定时器触发后如何执行回调？
  - 是否在IO线程执行，还是提交到其他线程？

**关键决策**：

- 定时器精度要求？
  - 毫秒级：最小堆足够
  - 微秒级：需要更精细的设计
- 定时器数量级？
  - 几百个：最小堆
  - 几万个：时间轮
  - 几十万个：分层时间轮

------

### 4. 线程模型

**目标**：合理分配IO线程和业务线程

**需要做的事情**：

- **IO线程**：
  - 数量？（通常是CPU核心数）
  - 如何分配连接？（轮询、负载均衡）
  - 是否支持动态调整？
- **业务线程池**：
  - 数量？（根据业务特点）
  - 任务队列大小？
  - 拒绝策略？（队列满了怎么办）
  - 优先级支持？
- **线程间通信**：
  - IO线程 -> 业务线程：提交任务
  - 业务线程 -> IO线程：发送响应
  - 使用什么机制？（无锁队列、条件变量）

**关键决策**：

- IO线程和业务线程是否分离？
  - 分离：更清晰，但有线程切换开销
  - 不分离：简单，但业务逻辑会阻塞IO
- 如果业务逻辑很快（微秒级），是否需要业务线程池？

------

## 第二步：协议层

### 5. 协议设计

**目标**：定义客户端和服务端之间的通信协议

**需要做的事情**：

- **协议头设计**：
  - 魔数（用于快速识别非法数据）
  - 版本号（协议升级）
  - 消息类型（请求、响应、心跳、错误）
  - 消息长度（用于粘包处理）
  - request_id（请求/响应匹配）
  - 序列化方式（protobuf、json等）
  - 压缩标志（是否压缩）
  - 校验和（可选，用于检测数据损坏）
- **协议体**：
  - 服务名
  - 方法名
  - 请求参数（序列化后的字节流）
  - 响应结果（序列化后的字节流）
  - 错误码和错误信息
- **协议解析**：
  - 如何从字节流中解析出完整的消息？
  - 如何处理半包？（数据还没收完）
  - 如何处理粘包？（一次收到多个消息）
  - 如何处理非法数据？（魔数不对、长度异常）

**关键决策**：

- 协议头是固定长度还是变长？
  - 固定长度：解析简单，但浪费空间
  - 变长：节省空间，但解析复杂
- 字节序？
  - 网络字节序（大端）
  - 主机字节序（小端）
- 最大消息长度限制？
  - 防止恶意攻击（发送超大消息）
  - 防止内存耗尽

------

### 6. 序列化层

**目标**：将对象序列化为字节流，以及反序列化

**需要做的事情**：

- **序列化接口抽象**：
  - 支持多种序列化方式（protobuf、json、msgpack）
  - 统一的序列化/反序列化接口
  - 如何注册新的序列化方式？
- **与protobuf集成**：
  - 如何根据服务名和方法名找到对应的protobuf类型？
  - 如何创建protobuf对象实例？
  - 反射机制？
- **性能优化**：
  - 是否需要对象池？（复用protobuf对象）
  - 是否需要零拷贝？
  - 是否需要压缩？（何时压缩？）

**关键决策**：

- 是否支持多种序列化方式？
  - 支持：更灵活，但增加复杂度
  - 只支持protobuf：简单，但不够灵活
- 如何处理protobuf的反射？
  - 使用protobuf自带的反射（性能较差）
  - 自己实现映射表（性能好，但需要手动注册）

------

## 第三步：RPC核心层

### 7. 连接管理

**目标**：管理客户端到服务端的连接

**需要做的事情**：

- **连接抽象**：
  - 连接状态（连接中、已连接、关闭中、已关闭）
  - 连接元数据（远程地址、本地地址、创建时间）
  - 发送队列（待发送的消息）
  - 接收缓冲区
  - 未完成的请求列表
- **连接池**：
  - 每个服务端地址对应一个连接池
  - 连接池大小？（最小、最大、初始）
  - 连接的获取策略？（轮询、最少连接、随机）
  - 连接的释放策略？（立即释放、延迟释放）
  - 空闲连接的清理？（多久没用就关闭）
- **连接建立**：
  - 异步连接（connect是非阻塞的）
  - 连接超时处理
  - 连接失败重试？（重试几次？间隔多久？）
  - DNS解析（同步还是异步？）
- **连接关闭**：
  - 优雅关闭（等待未完成的请求）
  - 强制关闭（立即关闭）
  - 半关闭（shutdown）
- **健康检查**：
  - 心跳机制（多久发一次？）
  - 失败检测（连续几次失败算不健康？）
  - 自动重连（连接断开后自动重连）

**关键决策**：

- 一个连接上同时有多少个未完成的请求？
  - 太少：无法充分利用连接
  - 太多：可能导致队头阻塞
- 连接池大小如何确定？
  - 根据QPS估算
  - 根据延迟估算

------

### 8. 请求/响应匹配

**目标**：将响应匹配到对应的请求

**需要做的事情**：

- **request_id生成**：
  - 全局唯一？还是每个连接内唯一？
  - 生成策略？（递增、随机、UUID）
  - 是否需要考虑回绕？（32位会回绕）
- **PendingCall管理**：
  - 数据结构（哈希表）
  - 并发访问保护（锁、无锁）
  - 内存管理（对象池）
- **超时处理**：
  - 每个PendingCall都有超时时间
  - 超时后如何处理？（触发错误回调）
  - 如何高效地检查超时？（定时器）

**关键决策**：

- request_id是32位还是64位？
  - 32位：节省空间，但可能回绕
  - 64位：不会回绕，但浪费空间
- PendingCall存储在哪里？
  - 每个连接一个map？（减少锁竞争）
  - 全局一个map？（简单，但锁竞争大）

------

### 9. Future/Promise实现

**目标**：提供异步编程接口

**需要做的事情**：

- **Promise设计**：
  - 存储结果（成功或失败）
  - 存储回调列表（可能有多个then）
  - 状态管理（pending、fulfilled、rejected）
  - 线程安全（多线程访问）
- **Future设计**：
  - 获取结果（get、wait）
  - 注册回调（then、on_error）
  - 组合操作（when_all、when_any）
  - 链式调用
- **回调执行**：
  - 在哪个线程执行回调？
    - IO线程？（简单，但可能阻塞IO）
    - 业务线程？（不阻塞IO，但有线程切换）
  - 如果回调抛异常怎么办？

**关键决策**：

- Future是否支持取消？
  - 支持：更灵活，但实现复杂
  - 不支持：简单
- Future是否支持超时？
  - get(timeout)
  - wait_for(timeout)

------

## 第四步：服务层

### 10. 服务注册

**目标**：让框架知道有哪些服务和方法

**需要做的事情**：

- **服务描述**：
  - 服务名
  - 方法列表
  - 每个方法的请求/响应类型
  - 方法的处理函数
- **注册机制**：
  - 手动注册？（用户调用RegisterService）
  - 自动注册？（通过宏或代码生成）
- **查找机制**：
  - 根据服务名和方法名查找处理函数
  - 数据结构？（两层map）
  - 性能优化？（缓存、预计算）

**关键决策**：

- 是否支持服务版本？
  - 同一个服务可能有多个版本
  - 客户端指定版本号

------

### 11. 请求分发

**目标**：将收到的请求分发到对应的处理函数

**需要做的事情**：

- **解析请求**：
  - 从协议中提取服务名、方法名
  - 反序列化请求参数
- **查找处理函数**：
  - 根据服务名和方法名查找
  - 如果找不到怎么办？（返回错误）
- **执行处理函数**：
  - 在哪个线程执行？
    - IO线程？（简单，但可能阻塞）
    - 业务线程？（不阻塞IO）
  - 如果处理函数抛异常怎么办？
- **发送响应**：
  - 序列化响应
  - 封装协议头
  - 写入发送缓冲区

**关键决策**：

- 是否支持异步处理函数？
  - 处理函数可能需要调用其他服务
  - 如何等待异步结果？

------

## 第五步：客户端层

### 12. Stub生成

**目标**：为每个服务生成客户端代理类

**需要做的事情**：

- **代码生成**：
  - 根据proto文件生成Stub类
  - 每个方法对应一个Stub方法
  - Stub方法内部调用RpcChannel
- **同步接口**：
  - 阻塞等待结果
  - 实现简单，但性能差
- **异步接口**：
  - 返回Future
  - 用户可以注册回调

**关键决策**：

- 是否同时提供同步和异步接口？
  - 同步：易用，适合简单场景
  - 异步：高性能，适合复杂场景

------

### 13. RpcChannel

**目标**：客户端的核心，负责发送请求和接收响应

**需要做的事情**：

- **发送请求**：
  - 序列化请求
  - 封装协议头
  - 选择连接（从连接池获取）
  - 写入发送缓冲区
  - 注册PendingCall
- **接收响应**：
  - 解析协议头
  - 根据request_id查找PendingCall
  - 反序列化响应
  - 设置Promise结果
- **错误处理**：
  - 网络错误
  - 超时错误
  - 协议错误
  - 业务错误

**关键决策**：

- 是否支持拦截器？
  - 在发送前/接收后执行自定义逻辑
  - 用于日志、监控、认证等

------

## 总结：第一步应该做什么？

**我的建议顺序**：

1. **先搭建网络IO层**：
   - Socket封装
   - 缓冲区管理
   - 基本的读写操作
2. **再实现Reactor**：
   - 事件循环
   - 事件注册和分发
   - 简单的echo server验证
3. **然后加入定时器**：
   - 定时器管理
   - 与Reactor集成
   - 验证超时功能
4. **接着设计协议**：
   - 定义协议格式
   - 实现协议解析
   - 处理粘包、半包
5. **再实现连接管理**：
   - 连接抽象
   - 连接池
   - 健康检查
6. **然后实现Future/Promise**：
   - 基本的Promise
   - Future接口
   - then链式调用
7. **最后串联起来**：
   - 实现RpcChannel
   - 实现服务注册和分发
   - 生成Stub代码
